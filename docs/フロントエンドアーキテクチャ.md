# CC Work History フロントエンド実装方針（renderer）

## 1. 概要

CC Work History の Electron renderer（React UI）の実装方針と要件を定めます。
Bulletproof React に倣った Feature-based アーキテクチャを採用し、保守性と拡張性の高いコードベースを構築します。

## 2. 技術スタック

### コア技術
- **Framework**: React 18 + Vite（Electron renderer）
- **Language**: TypeScript
- **Styling**: Tailwind CSS
- **State Management**: Zustand（UI 状態のみ）
- **Data Fetching**: preload が公開する `window.api`（IPC）を feature の `api/` でラップする
- **Database Client**: なし（DB アクセスは main プロセスのみ）
- **Form Management**: React Hook Form + Zod（設定画面、概要・タグ編集）
- **UI Components**: shadcn/ui（Radix UI ベース）

### 開発ツール
- **Linter/Formatter**: Biome
- **Testing**: Vitest + React Testing Library
- **E2E Testing**: Playwright（Electron サポート）

## 4. 機能要件

### Phase 1: MVP

#### 4.1 タイムライン表示
- **要件**:
  - 週単位のタイムラインを表示する（縦軸: 日、横軸: 時刻）
  - セッションを色付きの水平バーで表示する（バーの長さ＝活動時間）
  - プロジェクトごとに色分けする
  - 進行中のセッションを強調表示する
  - main からの更新通知を受けて自動で再描画する
- **表示項目**:
  - セッションバー（プロジェクト名、概要の先頭）
  - ホバー時のツールチップ（開始〜終了時刻、トークン数）
- **機能（初期スコープ）**:
  - 週の移動: 前週／翌週／今週ボタン
  - フィルタ・ソート: なし（Phase 2）

#### 4.2 セッション詳細表示
- **要件**:
  - 選択したセッションの詳細を右パネルに表示する
  - 基本情報（プロジェクト、開始・終了時刻、モデル、トークン数、メッセージ数）と状態を表示する

### Phase 2: 機能拡張
- 自動生成された概要・タグの表示と手動編集
- 色分け基準の切り替え（プロジェクト／タグ／ステータス）
- 期間・プロジェクト・タグによるフィルタと検索
- ズーム・パン操作

### Phase 3
- ダッシュボード（統計カード、日別グラフ、プロジェクト別サマリー）
- 成果情報（コミット数・変更ファイル数）と作業状況チェックリスト
- セッション一覧画面、セッション再開、概要の Markdown コピー、設定画面

## 5. 非機能要件

### パフォーマンス
- 数百〜数千セッションの履歴でも快適に操作できること
- 1 週間分のデータだけを取得・描画し、全件を renderer に渡さない
- セッションバーの再描画は表示中の週に限定し、リアルタイム更新で画面全体を再描画しない
- 暫定目標: 週の切り替え・ズームがユーザーに待ちを感じさせないこと（実測して目標値を決める）

### アクセシビリティ
- キーボード操作対応（週の移動、セッション選択、パネル操作）
- 色だけに頼らない区別（進行中セッションはアイコン・枠線でも示す）
- 適切な ARIA 属性の使用

### テーマ
- ライト／ダークの両テーマに対応し、設定画面で切り替えられる（OS 設定にも追従可能）

## 6. 実装ガイドライン

### コーディング規約
1. **コンポーネント設計**
   - 単一責任の原則
   - Props Interface の明確な定義
   - コンポーネントの適切な分割
2. **型定義**
   - 全てのコンポーネントで TypeScript を使用
   - any 型の使用禁止
   - IPC の DTO 型は `src/shared/` から import する
3. **スタイリング**
   - Tailwind CSS のユーティリティファースト
   - 条件付きクラスは `cn()` ヘルパーで組み立てる
   - 詳細は `スタイルガイド.md` を参照

### アーキテクチャ原則
1. **Feature-based 構造**: 機能ごとにモジュール化
2. **明確な責任分離**: API、Components、Hooks、Types の分離
3. **依存関係の管理**: feature 同士は直接 import せず、pages で組み合わせる。循環参照を避ける
4. **テスタビリティ**: 座標計算・色割り当てなどは `utils/` の純粋関数に切り出してテストする

## 7. 実装順序

1. **基盤構築**
   - preload と `window.api` の型設定
   - 共通 UI コンポーネント（shadcn/ui）のセットアップ
   - アプリシェル・サイドナビの実装
2. **timeline Feature 実装**
   - 型定義 / API フック / 座標変換 utils / コンポーネント
3. **session-detail Feature 実装**
4. **ページ実装**
   - メイン画面の 2 ペイン構成への統合

## 8. テスト戦略

### ユニットテスト
- utils の純粋関数（時刻 ↔ 座標変換、週の区切り、色割り当て）
- カスタムフック
- 表示だけのコンポーネント

### 統合テスト
- `window.api` をモックした feature 単位のテスト
- ページコンポーネント

### E2E テスト（対象スコープ）
- 起動からタイムライン表示まで
- セッション選択と詳細パネルの表示・編集

## 9. ビルド・配布

- **ビルド**: Vite で renderer をビルドし、electron-builder でパッケージする
- **環境変数管理**: 開発時のみ `.env` で Stub 切り替えやログディレクトリを上書きする。本番ビルドに秘密情報を含めない
- **CI/CD**: GitHub Actions（`pnpm verify`）
- **配布**: macOS / Windows / Linux 向けのインストーラ（詳細は `インフラストラクチャ規約.md`）
