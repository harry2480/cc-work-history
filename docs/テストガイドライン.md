# CC Work History テストガイドライン

このドキュメントは、CC Work History におけるテストの書き方と運用方法をまとめたガイドラインです。基本ルールは `CLAUDE.md` と `品質チェック・テスト規約.md` にも書かれています。

## テストの種類と構成

以下の種類のテストを、開発フェーズに合わせて段階的に導入します。

| 種類 | 配置場所 | 実行環境 | 実行コマンド | 用途 | 状態 |
|------|----------|----------|-------------|------|------|
| ユニットテスト | `apps/desktop/test/unit/**/*.test.ts` | Vitest | `pnpm test:unit` | domain・application・renderer の純粋関数のテスト | 未導入（Phase 1 で導入） |
| DBロジックテスト | `apps/desktop/test/integration/infrastructure/repositories/` | Vitest + Node.js | `pnpm test:integration` | SQLite のマイグレーション・Repository・集計クエリの検証 | 未導入（Phase 1 で導入） |
| 統合テスト | `apps/desktop/test/integration/` | Vitest + Node.js | `pnpm test:integration` | JSONL 取り込み〜DB 保存のシナリオテスト | 未導入（Phase 1 で導入） |
| E2Eテスト | `apps/desktop/test/e2e/` | Playwright（`_electron`） | `pnpm test:e2e` | 起動・タイムライン表示・詳細パネルのフロー検証 | 未導入（Phase 2 以降） |

テストのパスはソースのディレクトリ構造をミラーします（例: `src/main/backend/domain/models/session.model.ts` → `test/unit/main/backend/domain/models/session.model.test.ts`）。

## CI実行フロー

PR が作成されると、`.github/workflows/ci.yml` で以下が順に実行されます。

```text
PR Created / Push
  └── verify
      ├── pnpm lint（フォーマット + lint）
      ├── pnpm typecheck（TypeScript 型チェック）
      ├── pnpm test:unit（ユニットテスト）
      ├── pnpm depcruise（依存方向チェック）
      └── pnpm test:integration（SQLite・フィクスチャを使う統合テスト）
```

全ステップがパスするとマージ可能になります。

## ユニットテスト

### 対象
- ドメインモデル・ドメインサービス（`src/main/backend/domain/`）
- UseCase（`src/main/backend/application/`）。Gateway・Repository はモックする
- renderer の純粋関数（`src/renderer/lib/`、各 feature の `utils/`）
- 例: ログ行からのセッション組み立て、トークン数の集計、アイドル時間によるセッション区間の分割、時刻 → タイムライン座標の変換、色の割り当て

### 配置ルール
`test/unit/` 配下に、ソースと同じ階層で `*.test.ts` として配置します。

```text
apps/desktop/
├── src/main/backend/domain/models/
│   └── session.model.ts
└── test/unit/main/backend/domain/models/
    └── session.model.test.ts    ← ソース構造をミラー
```

### ポイント
- **mock は極力使わない**: 対象のロジックを純粋関数やモデルのメソッドとして切り出してからテストする。
- **ローカルで動くものは real で動かす**: SQLite は一時ファイルまたは `:memory:` の実 DB に接続してテストする（統合テスト側）。
- **外部プロセスは DI でモックする**: Claude CLI・git・ターミナル起動は Gateway interface 越しに呼び、テストでは Stub/Mock 実装に差し替える。
- **時刻を固定する**: 進行中判定や週の区切りなど現在時刻に依存するロジックは、時刻を引数で受け取るか `vi.useFakeTimers()` で固定する。

## DBロジックテスト（未導入）

### 対象
- マイグレーション（空の DB から最新スキーマまで適用できること）
- Repository の CRUD と、期間・プロジェクト・タグによる絞り込み
- ダッシュボード用の集計クエリ

### 前提
- テストごとに一時ディレクトリへ新しい SQLite ファイルを作り、マイグレーションを適用する
- better-sqlite3 はテスト実行環境（Node.js）の ABI でビルドされていること

### 設計方針
集計クエリは境界値（期間の端にまたがるセッション、終了時刻のない進行中セッション）を必ずテストします。

## 統合テスト（未導入）

### 対象
- JSONL 取り込み UseCase（フィクスチャ JSONL → 解析 → DB 保存）
- ファイル監視から再取り込みまでの流れ
- IPC の loader / action（Electron を起動せず、ハンドラ関数を直接呼ぶ）

### 設計原則
#### 1. 依存関係（DB 接続など）を DI する
UseCase は Repository・Gateway をコンストラクタで受け取る設計にする。

#### 2. 外部プロセスは Stub で差し替える
Claude CLI の呼び出しは Stub 実装を注入し、固定の概要・タグを返す。

#### 3. DB 状態を必ず検証する（最重要）
**関数の戻り値だけでなく、DB の状態を必ず検証する。** これにより、実際にデータが永続化されたことを保証する。

```typescript
// 良い例: DB状態も検証
await importSessionLogsUseCase.execute({ projectDir: fixtureDir });

const session = sessionRepository.findById('fixture-session-1');
expect(session?.messageCount).toBe(12);  // DBに反映されたことを確認
```

#### 4. エラーケースの DB 状態検証
壊れた JSONL 行が含まれる場合に、その行だけをスキップし、既存データが壊れていないことを DB レベルで確認する。

#### 5. クリーンアップを徹底する
一時ディレクトリと SQLite ファイルは `afterEach` で必ず削除する。

### フィクスチャ
- 実際の Claude Code ログから個人情報・プロンプト本文を取り除いた最小限の JSONL を `test/fixtures/` に置く
- 実ログをそのままコミットしない

## E2Eテスト（未導入）

### 対象
- アプリ起動 → フィクスチャのログがタイムラインに表示される
- セッションを選択 → 詳細パネルに概要・タグが表示される → 編集して保存できる

### 設計方針
- Playwright の Electron サポート（`_electron.launch`）を使用
- ログディレクトリと `userData` はテストごとの一時ディレクトリに向ける
- Claude CLI は Stub に切り替えて実行する
- CI ではアプリのビルド後に実行

## テスト作成時の注意事項

### テスト追加が必要なケース
以下のケースではテスト追加が必須です：
- JSONL の解析ロジックの変更（ログ形式の変化に追従したときを含む）
- セッションの時間・トークン集計ロジックの変更
- DB スキーマ・マイグレーションの変更

加えて、以下のケースでもテスト追加を推奨します：
- 新しいユーティリティ関数の追加
- 既存ロジックのリファクタリング（回帰テストとして）
- バグ修正（再発防止テストとして）

### describe/it の構造化
関連するケースは `describe` でグループ化し、意図を明確にします。

### 一意性の確保
テストデータの ID には `Date.now()` やランダムな UUID などを含めて、並列実行時の重複・衝突を防ぎます。

### PR 前の確認
```bash
# 開発中に手元で実行・確認
pnpm test:unit --watch

# PR 作成前に全チェックを実行
pnpm verify
```
